# Taste
- Prefers read-only audit and investigation mode when requested: do not modify source code, tests, configuration, migrations, or documentation until explicitly authorized to implement. Confidence: 0.95
- Requires open, unresolved, contradictory, future, or optional requirements to be treated as documentation decisions requiring product/technical owner approval, never as automatic implementation work unless docs explicitly require them. Confidence: 0.95
- Wants every audit finding classified into exactly one triage category (confirmed bug/security/invariant break vs. engineering improvement vs. missing frozen requirement vs. decision-required vs. technical debt vs. optional improvement vs. false-positive/acceptable) with explicit rationale for the placement. Confidence: 0.9
- Wants remediation backlogs reported with full traceability per item — finding ID, category, severity, evidence, affected files, requirement/document reference, recommended action, dependencies, and whether owner approval is required — then prioritized P0/P1/P2/P3. Confidence: 0.9
- Before any code changes, wants the whole project loaded and understood first (structure, docs, architecture, app flow, domain models/rules, endpoints, DB/ORM/migrations, auth, conventions, DI/config, error handling, tests, integrations, deployment, git state, and project instruction files like AGENTS.md/CLAUDE.md) — investigation is the explicit first priority, not immediate modification. Confidence: 0.95
- Strongly prefers preserving the project's existing design and conventions: do not rewrite, refactor, or "improve" existing code just because a different approach is preferred; change only what the task explicitly requires. Confidence: 0.95
- Wants architecture/patterns inferred from the actual codebase rather than assumed from standard conventions. Confidence: 0.9
- Wants a concise project-context summary delivered before the task begins, covering project purpose, architecture, tech stack, main modules/features, important business rules, conventions, key files/directories, and risks/inconsistencies. Confidence: 0.85
- Wants explicit call-outs of forces/business invariants that must NOT be changed without justification. Confidence: 0.8
- Prefers long-form deliverables persisted as markdown (.md) files rather than chat-only output. Confidence: 0.7
- Prefers AI working artifacts/backlogs kept private between user and assistant, not committed into the project repo (keep git status clean; save outside repo e.g. Desktop and return explicit file path). Confidence: 0.95
- Treats the project's business documentation (PRD, functional requirements, user stories, invariants, architecture rules, project instruction files) as the authoritative source of truth when auditing whether code behaves correctly. Confidence: 0.9
- Wants audit findings delivered in a consistent structured block per issue: severity (Critical/High/Medium/Low), exact location (file + class/handler/method), business rule involved, expected vs actual behavior, why it is a problem, a concrete reproduction scenario, recommended solution, and documentation impact. Confidence: 0.9
- Wants correctness verified by tracing the complete flow end to end (request → controller/API → command/query → handler → domain/application logic → database → external services → response) rather than by reviewing code in isolation. Confidence: 0.85
- Wants documentation/implementation contradictions or ambiguities surfaced explicitly instead of being silently resolved by guessing. Confidence: 0.85
- Wants audits to be exhaustive rather than stopping at the first issues, and to end with a categorized summary (critical/high/medium-low issues, business-rule violations, architecture violations, security concerns, data-consistency/concurrency concerns, documentation inconsistencies, prioritized recommendations) plus per-dimension numeric scores. Confidence: 0.8
